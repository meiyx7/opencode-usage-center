# TASK-17.2 瓶颈分析、优化建议与预期收益（先不改代码）

基线：`aa2f14b9d02d1d28ebd9cf8ff68bd19ec1f88848`。数据来源：`docs/TASK17_1_BASELINE.md`、
`docs/perf/TASK17_1_raw.json`（3 次独立子进程重复测量）。本文件**只分析、只建议，不修改任何代码**。

## 1. 结论先行

**没有找到需要改生产代码的可重复性能瓶颈。** 按生产真实链路，10,000 回合完整翻完 167 页耗时 **0.562s**（中位数），单页服务端 p50 **1.07ms**，前端合并单页 p50 **0.16ms**。任务书里 67.3s 的「全链」不是分页链路慢，而是既有 15g 测试夹具在**每一页都传了 `force:true`**，把全会话汇总 SQL 重算了 167 遍 —— 本机复现为 47.88s，`summary.scalars` / `toolStats` 各执行 167 次；同样 167 页在生产语义下各只执行 1 次。

唯一成本高且可重复的环节是**冷首屏 288ms 的全会话汇总**（`toolStats` 175.5ms + `scalars` 104.6ms），但它被 `sessionCache`（4 条 / 60s）挡住，只在首次打开、`force` 刷新、TTL 过期、Revert 后发生；翻页不受影响。**不建议为此改动统计 SQL**：改动面涉及统计口径与 schema 约束，收益只作用于每会话每 60s 最多一次的路径。

按「不能为了完成任务而制造没有实际收益的代码改动」，本阶段建议 **TASK-17.3 不实施生产代码优化**，只把测量口径修正与内存边界作为候选项交复审决策。

## 2. 瓶颈定位（全部用实测数据）

### 2.1 服务端

| 环节 | 实测 | 判定 |

| `buildSessionSummary` 全会话汇总 | 冷−热 = 287.18ms（中位数），占冷首屏 99.6% | **真实成本，但被缓存隔离** |
| ├ `summary.toolStats`（`json_each` 展开 30,000 个 content 元素） | 175.50ms/次 | 汇总内 62.3% |
| └ `summary.scalars`（10,000 行 × 11 `json_extract`） | 104.62ms/次 | 汇总内 37.1% |

| seq 游标 / user 边界 / 回合计数 | 7 条查询在真实 216MB 库上全部 `SEARCH ... USING INDEX`，无表扫描、无临时排序；逐页耗时平坦（首末 281.61/282.06ms，`cache` 链首末 286.14/0.596ms） | 索引稳定，无 O(n²) 退化 |
| JS 回合对象构建 | 热首屏 0.59ms / 60 回合 | 不是瓶颈 |
| 重复扫描 / 无效查询 | `cache` 链 167 页只做 1 次汇总；`force` 链 `page.firstMessage` 每页 2 次（汇总一次 + 页探测一次）；`page.headRow` + `turnStartOffset` 各 166 次 | 冗余查询合计 <1ms/页，**不值得改** |
| 汇总 `ORDER BY seq` | 查询计划由 `(session_id,type,seq)` 索引满足，无 `TEMP B-TREE`；JS `percentile()` 内部自行 `sort`，求和与分位数都不依赖 SQL 行序 | 去掉它收益≈0，且会动 SQL 文本与 15h 断言 → **不做** |

`force` 链服务端累计 47.75s 的 98.7% = `toolStats` 29.57s + `scalars` 17.54s（167 次重复），这是**重复执行**造成的，不是单次 SQL 慢；其余翻页 SQL 仅 252.8ms、JS 385.1ms。`cache` 链服务端累计 464.6ms，其中汇总 282.0ms、翻页 SQL 129.9ms、JS 52.7ms。

### 2.3 缓存

| 项 | 结论 |
| --- | --- |
| 服务端 `sessionCache` 命中率 | `cache` 链 167 页中 166 页命中（99.4%）；命中确实跳过了两条汇总 SQL，不是「缓存了但仍解析」 |
| 前端 `DETAIL_CACHE` | 4 条 / 120s / `delete+set` LRU，由 16m/16q 覆盖；`dispose()` 故意不清缓存，重开可复用 |
| 不必要的序列化/复制 | `wire()` 每页 `JSON.parse(JSON.stringify(detail))` 1.11MB / 0.50ms，全链 176.8MB。这是插件 RPC 契约的净化往返，不是重复解析消息正文；改它需要动协议（禁止） |
| 缓存命中是否避免重复解析 | 是：全链 JSON 解析恰好 20,000 次（每条消息一次），两种链模式完全相同 |
| 汇总正文传入 JS | 恒 0 字节（3 次 × 所有阶段） |

### 2.4 内存（必须区分「真实」与「测量造成的」）

峰值 1,212MB 是 **Bun 进程内**的高水位，不是浏览器堆；测量脚本在同一进程连续跑完两条 167 页全链、保留一份 10,000 回合 detail、再依次做全量搜索 / CSV / JSON 导出，比单个真实视图持有更多 transient 对象，且 Bun 的 GC 回收时机放大了 RSS 高水位。

可复现的真实大对象只有两个：

1. **全量搜索索引**：+237MB RSS（943 − 706）。10,000 个回合各缓存一份约 9KB 的搜索 blob（text 6,000 + reasoning 1,500 + tool input/output 等裁剪上限）。
2. **全量 JSON 导出**：`buildJsonPayload(..., full=true)` 产出 **172.6MB** 字符串，序列化后 +246MB RSS（1,212 − 966）。CSV 仅 1.30MB / +23MB。

这两项都由「用户把 10,000 回合全部加载完再搜索/导出」触发，是导出/搜索语义的直接结果；**缩小它们必然改变搜索命中字段或导出内容/范围，与禁止事项冲突**。因此记录为 P2 边界，不在本批次优化。

### 2.5 Revert / Delete / dispose 后无效数据保留

静态核查 + 16p/16q 既有确定性用例：

| 路径 | 行为 | 是否残留 |
| --- | --- | --- |
| Revert committed（页面层） | `invalidateDetailCache(sessionID)` + 标脏会话；详情页层 `invalidate` + `forceReload` | 前端缓存立即失效；服务端汇总由 `force` 重算，无旧数据 |
| Revert cleared | 只消费脏标记，不清缓存、不刷新（16.3 修复） | 无多余动作 |
| Delete（页面层 + 详情页层） | 前端缓存按会话失效；`markGone` → `cancelForGone()` 作废在途、复位加载态；消费循环 `break` | 前端无残留 |
| Delete（服务端 `sessionCache`） | **没有按会话主动失效**，条目最多保留 60s 或被 4 条 LRU 挤出 | 有界残留，且删除后 `sessionGone` 短路所有 load/loadMore，不会被读到；无正确性问题 → P3 |
| dispose | 只置 `disposed` 标志 + 作废在途，**故意不清有效缓存** | 有意保留，供重开复用；16q 已验证 |

## 3. CI「67.3s」的性质（重要）

- 15g 用例（`scripts/check-synthetic.ts:1027`）循环里每页都写 `force: true`，而生产 `createDetailLoader.loadMore()`（`src/gui/session-detail.tsx:348`）只发 `{ sessionID, beforeTurn }`，**从不带 force**。
- 本机同 fixture：`force` 链 47.88s（167 次汇总）vs `cache` 链 0.562s（1 次汇总），**85×**；CI 403ms / 67.3s 与本机 288ms / 47.88s 的比值同为 1.40× / 1.41×，确认是同一路径的机器差异。
- 因此 67.3s **不能作为生产性能退化的证据**，也不能据此推导「需要优化分页」。它衡量的是「强制每页重算全会话汇总」这一测试设定。

## 8. TASK-17.3 执行结果（O-1 已实施，2026-11-15）

O-1（15g 夹具口径修正）已按复审意见实施，**生产代码零改动**：

- **修正内容**：15g 首屏保留 `force:true`（冷汇总路径仍被覆盖）；167 页翻页去掉 `force:true`，与生产 `loadMore()` 语义一致；新增 SQL 执行计数探针与 8 条断言（翻页汇总 SQL 0 次、无缺失/无重复等）；新增 17a 缓存行为独立测试块（12 条断言：建缓存 / 命中 0 次 / force 绕过 1 次 / 刷新后重新命中 / 四路径统计一致）。详见 `TASK17_1_BASELINE.md` §12。
- **缓存行为最终表述**：正常翻页复用汇总缓存不重复计算；缓存未命中或 TTL 过期（60s）时重新汇总；显式强制刷新和 Revert committed 绕过缓存重新汇总，不受 TTL 限制。
- **三种口径必须区分**：①旧 force-every-page（47.88s / CI 67.3s，仅历史对照）；②修正后生产语义分页（435–447ms，15g 现行）；③冷首屏 288.46ms / 热首屏 1.23ms / 强制刷新（check-perf 单请求口径，生产代码未变故数字不变）。
- **声明**：synthetic 总耗时 ~50s → ~2.4s 是**测试口径修正**，不是生产代码性能提升；本轮 `src/` 零改动。
